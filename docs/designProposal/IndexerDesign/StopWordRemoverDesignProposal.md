# StopWordRemover Design Proposal
---

# Overview

The **StopWordRemover** component is responsible for removing commonly used stop words from the token list generated by the Tokenizer.

Stop words are frequently occurring words that usually provide limited value during search indexing, such as articles, prepositions, and auxiliary verbs.

The component reduces unnecessary terms before the Inverted Index construction stage, improving indexing efficiency while preserving meaningful searchable terms.

## Responsibilities

The StopWordRemover is responsible for:

- Maintaining a predefined collection of stop words.
- Checking each token against the stop-word collection.
- Removing tokens that do not provide meaningful search information.
- Preserving the order of remaining terms.
- Preserving duplicate terms required for frequency calculation.
- Passing filtered terms to the InvertedIndex component.

## Non-Responsibilities

The StopWordRemover does not handle:

- HTML parsing.
- Text extraction.
- Tokenization.
- Lowercase conversion.
- Punctuation removal.
- Stemming or lemmatization.
- Inverted index construction.

---

# Section 1 – Public API

## Public Interface

```cpp
class StopWordRemover
{
public:

    DynamicArray<string> removeStopWords(
        const DynamicArray<string>& tokens);
};
````

### Method Description

| Method              | Parameters                           | Return Type            | Description                                                                                |
| ------------------- | ------------------------------------ | ---------------------- | ------------------------------------------------------------------------------------------ |
| `removeStopWords()` | `const DynamicArray<string>& tokens` | `DynamicArray<string>` | Removes predefined stop words from the input tokens and returns filtered searchable terms. |

### Why this API?

The StopWordRemover is responsible only for filtering predefined stop words.

It does not:

* Tokenize text.
* Normalize words.
* Build the inverted index.

Separating these responsibilities keeps the component modular, reusable, and easy to maintain.

# Section 2 – Internal Representation

The StopWordRemover maintains an internal `HashMap<string, bool>` containing predefined English stop words.

The HashMap is initialized during object construction and is used for efficient lookup while processing tokens.

## Processing Rules

* Each token is searched in the stop-word HashMap.
* If the token exists in the HashMap, it is removed.
* Otherwise, it is considered a valid searchable term and added to the output `DynamicArray<string>`.
* The original order of remaining terms is preserved.
* Duplicate terms are preserved because they are required for frequency calculation in the InvertedIndex.

---

# Section 3 – Failure Handling

| Situation                    | Handling Strategy                       |
| ---------------------------- | --------------------------------------- |
| Empty input array            | Return an empty `DynamicArray<string>`. |
| Empty token                  | Ignore the token.                       |
| All tokens are stop words    | Return an empty `DynamicArray<string>`. |
| Token not present in HashMap | Treat it as a valid searchable term.    |

The StopWordRemover continues processing all remaining tokens even if some tokens are discarded.

# Section 4 – Complexity Analysis

Let **n** be the number of input tokens.

| Operation          | Best Case | Average Case | Worst Case |
| ------------------ | --------- | ------------ | ---------- |
| Stop-word Lookup   | O(1)      | O(1)         | O(n)       |
| Complete Filtering | O(n)      | O(n)         | O(n²)      |

Since each token requires one HashMap lookup, the practical complexity of stop-word removal is:

```text
O(n)
```

for a properly distributed hash function.

The theoretical worst case can become:

```text
O(n²)
```

if all tokens experience severe hash collisions.

# Section 5 – Future Compatibility

The StopWordRemover produces the filtered list of searchable terms that are consumed by the **InvertedIndex** component.

```text
HTMLParser
      │
      ▼
Tokenizer
      │
      ▼
StopWordRemover
      │
      ▼
DynamicArray<string>
      │
      ▼
InvertedIndex
```

Future improvements such as:

* Configurable stop-word dictionaries.
* Language-specific stop-word lists.
* User-defined stop words.

can be added without changing the public API or affecting other Indexer components.
